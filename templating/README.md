# SMART TRAFFIC — лабораторная №2

Три SSR-страницы теперь читают PostgreSQL. Исходный дизайн сохранён; добавлены поиск по названию, удаление и кнопки создания/публикации. Данные `data/collections.py` служат архивом первой лабораторной и не импортируются приложением.

## Запуск

Из `/home/tsoriev_nv/RIP/templating`:

```bash
../venv/bin/pip install -r requirements.txt
# На новой машине: скопировать .env.example в .env.
docker compose up -d
../venv/bin/alembic upgrade head
../venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000
```

Открыть http://localhost:8000/grid и http://localhost:8081.
В Adminer: **PostgreSQL**, сервер **postgres**, пользователь **myuser**, пароль **mypassword**, база **smart_traffic**. Параметры задаются в `.env`.
При первой установке: Adminer → SQL-команда → вставить содержимое `sql/seed.sql` → Выполнить (либо импортировать этот файл). Импорт не перезаписывает существующие строки. Не требуется запускать seed при каждом старте.

PostgreSQL опубликован на `localhost:5432`, как в методичке. Между контейнерами используется `postgres:5432`. pgAdmin не используется. Старый контейнер `postgres_db` остановлен, его автозапуск отключён (`restart=no`), данные сохранены. Не запускайте его одновременно с PostgreSQL лабораторной: он также настроен на порт 5432.

Исходные фото/видео семи карточек остаются в существующем MinIO:

```bash
docker start minio_storage
```

Конфигурация MinIO по-прежнему в `../docker-compose.yml`. В БД перенесены полные URL исходных объектов. При открытии сайта с другого компьютера замените `localhost` в этих URL на адрес SSR/MinIO-сервера. При пустой ссылке или ошибке загрузки HTML подставляет локальные `/static/img/default.jpg` и `/static/video/default.mp4`.

## Поведение

- 7 демонстрационных пользователей (`demo_1`–`demo_7`); лайки распределены между ними.
- 7 исходных опубликованных устройств, ID 1–7; удалённое ID 8; демонстрационный черновик ID 9 принадлежит пользователю 7.
- Демо-пользователь приложения — ID 1 (`CURRENT_USER_ID`); авторизация не входит в ЛР2. Первый GET `/add` ничего не создаёт.
- «Далее» создаёт один черновик. Повторный POST не создаёт второй. Блокировка пользователя и частичный уникальный индекс защищают от параллельных запросов.
- Существующий черновик открывается с заполненными полями и кнопкой «Опубликовать». Нужны описание, E(X), D(X). Дата формирования устанавливается при публикации, дата создания сохраняется.
- Файлы выбираются только локально. У file-input нет `name`; форма не отправляет файлы, URL или имена файлов. Новые карточки имеют NULL в media URL и показывают локальные заглушки.
- Каталог и лента показывают опубликованные карточки. URL удалённой, чужого черновика и несуществующей записи возвращает 404.
- Лайки только отображаются и подсчитываются в БД. Менять их для демонстрации нужно через Adminer.
- Статусы: `draft` — черновик, `published` — опубликован, `deleted` — удалён.

## Шесть контроллеров

| Метод | URL | Назначение | Доступ к данным |
|---|---|---|---|
| GET | `/feed?id=1` | Просмотр и следующее устройство | ORM SELECT |
| GET | `/grid?search=Xiaomi&mean_max=20` | Список, поиск и фильтр | ORM SELECT |
| GET | `/add` | Чтение черновика | ORM SELECT |
| POST | `/add` | Создание черновика | ORM add/commit |
| POST | `/device/{id}/publish` | Публикация | ORM SELECT и изменение объекта |
| POST | `/device/{id}/delete` | Логическое удаление | Параметризованный SQL UPDATE RETURNING |

Контроллеры находятся в `api/handlers.py`. SQL-удаление выполнено через `AsyncSession.execute(text(...))` и результат `fetchone()`, как в методичке: ORM update/delete не используется. `/` — технический redirect в middleware, не дополнительный бизнес-контроллер.

## Структура БД и ERD

`models/` — единственные определения таблиц; `db/base.py` — единственная декларативная база. `core/config.py` читает Pydantic Settings; `db/session.py` создаёт асинхронные сессии SQLAlchemy с asyncpg. `alembic/` содержит исходные миграции и дополнительную `b219_lab2`.

Таблицы: `users`, `smart_devices`, `likes` (плюс служебная `alembic_version`). У лайков отдельный PK и два обязательных FK, пара user/device уникальна. Каскадных удалений нет. Два предметных поля — `traffic_mean` и `traffic_variance`; `type_label` и `model` сохраняют подписи интерфейса. Один черновик на создателя обеспечен частичным уникальным индексом PostgreSQL.

Открыть `docs/smart_traffic.mdj` в StarUML → Data Model → «Таблицы и связи». Файл содержит ERD, колонки с типами/длинами, PK/FK и три связи 1:N. Создан в формате StarUML; открытие в GUI следует проверить перед сдачей. Для числовых типов и timestamp длина VARCHAR не применяется.

## Проверка

Интеграционный сценарий работает только с отдельной БД, имя которой заканчивается `_test`:

```bash
../venv/bin/pip install httpx
docker compose exec -T postgres createdb -U myuser smart_traffic_test
DB_NAME=smart_traffic_test ../venv/bin/alembic upgrade head
DB_NAME=smart_traffic_test PYTHONPATH=. ../venv/bin/python tests/integration.py
../venv/bin/alembic check
```

Проверяются шесть контроллеров, семь исходных карточек, поиск/фильтр, отсутствие записи после GET добавления, повторное создание черновика, валидация, публикация, дата формирования, отражение SQL-изменений и количества лайков, удаление, 404 и ограничения БД. Тестовые записи остаются только в тестовой БД.

Сценарий защиты и контрольные вопросы: `docs/defense.md`. Примеры SELECT/UPDATE: `sql/demo.sql`.

Справочные источники: [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html), [официальный формат примера ERD StarUML](https://github.com/staruml/staruml-samples/blob/main/ERDExample.mdj).
